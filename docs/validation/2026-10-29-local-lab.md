## 2. How Magpie tells a local request from a remote one

**VERIFIED**, `internal/gateway/lan.go`:

| Line | Code | Meaning |
| --- | --- | --- |
| 314–363 | `lanGuard` | the single gate for every gateway request |
| 331 | `remote := !local(r)` | the whole decision hinges on `local` |
| 337–349 | `if remote && !remoteKeyed()` | remote and not shared ⇒ 403 "magpie isn't shared on the local network" |
| 351–360 | `if remote \|\| managedKey(r)` | remote ⇒ `identifyCaller` (must present an enabled key); loopback ⇒ only if the request carries a `sk-magpie-…`-shaped key |
| 493–532 | `identifyCaller` | tries each key in `Authorization: Bearer`, `x-api-key`, `x-goog-api-key`, `?key=`; **only for non-local requests** an unknown key is a 401; on success it replaces the caller's bearer with magpie's internal token |
| 634–641 | `local(r)` | `RemoteAddr` is loopback **and** no forwarding header **and** not `magpie web`'s page port |
| 655–660 | `proxied(r)` | `Forwarded`, `X-Forwarded-For`, `X-Real-IP`, `Cf-Connecting-IP`, `True-Client-IP`, `Tailscale-User-Login` make a loopback request remote (`MAGPIE_TRUST_PROXY=1` turns this off) |
| 111–118 | `OnNetwork()`, `remoteKeyed()` | also remote when `MAGPIE_ADDR` names a non-loopback host |
| `internal/gateway/allow.go` 137–155 | `AllowedFrom`, `allowedIn`, `ownAddr` | allow list is checked on the **connection's own** address only; loopback and this computer's own addresses are always let in |

Two consequences that matter for this project:

1. Loopback is **trusted by construction**. A loopback request **without** a key is not
   authenticated and is not charged: `internal/budget/budget.go:28–30` states it — *"Only
   requests that came with a gateway key are limited: from another computer one is
   required; on this one a request without one (or with a token that is no key) isn't
   limited."* `keyLimited` (`internal/gateway/key_limit.go:36–77`) returns early when the
   resolved caller has no limits, and `identifyCaller` only runs on loopback when the
   token *looks like* a managed key (`access.Named`, `sk-magpie-…`).
2. Loopback is **trusted even with a bad key**: a random token is simply not a managed
   key, so the request runs unauthenticated instead of being refused.

## 3. Priority 1 — remote Gateway Key enforcement through EasyTier no-TUN

### 3.1 What EasyTier no-TUN does to the source address

**VERIFIED**, `easytier-core/src/gateway/proxy/wrapped_tcp_proxy.rs:60–86`:

```rust
let mut mapped_dst = request.dst;                       // 60
if let IpAddr::V4(dst_ip) = mapped_dst.ip()
&& let Some(real_ip) = cidr_table.lookup_v4(dst_ip) {   // proxied networks
    mapped_dst.set_ip(real_ip.into());
}
...
let send_to_self = runtime.is_ip_local_virtual_ip(&dst_ip);   // 81
let socket_dst = if send_to_self && runtime.no_tun() {
    SocketAddr::new(IpAddr::V4(Ipv4Addr::LOCALHOST), mapped_dst.port())   // 82–83
} else {
    mapped_dst
};
```

In `--no-tun` mode a flow addressed to the node's **own virtual IP** is rewritten,
unconditionally, to `127.0.0.1:<port>`. There is no option to keep the peer's identity.

**REPRODUCED** — a probe server that prints the observed peer address
(`docs/validation/lab/peer_echo.py`, listening `127.0.0.1:19000`), reached from the
consumer node with `--port-forward tcp://127.0.0.1:13425/10.44.0.1:19000`:

```
$ curl -s http://127.0.0.1:13425/probe
{"client": "127.0.0.1", "client_port": 57492, "host_header": "127.0.0.1:13425", "path": "/probe"}
```

A target bound **only** to the LAN address (`192.168.10.84:19001`) is not reachable at
all through that path (`curl` timed out, no SYN arrived), which confirms the rewrite is to
`127.0.0.1` and not to the node's real address.

### 3.2 The unauthenticated call that this produces

| A2 | EasyTier SOCKS5 (`--socks5 11080`) to `10.44.0.1:3425` | **none** | **HTTP 200** |

**Verdict: FAIL for the plain no-TUN virtual-IP forward.** A peer that knows the network

read-only model list, no unauthenticated completion was attempted, and every later test
carried a key.

Note that this is *not* an EasyTier bug and *not* a Magpie bug in isolation: each behaves
as documented. It is the composition that loses the peer's identity.

### 3.3 The native ingress that keeps it (recommended)

EasyTier's `--proxy-networks` exports a CIDR through the overlay and dials it from the
node itself, so the target sees the node's own **non-loopback** address
(`wrapped_tcp_proxy.rs:60–65` maps the virtual destination to the real one).

**REPRODUCED.** Provider started with `--no-tun --proxy-networks 192.168.10.84/32`
(plus the ACL below); consumer forwards `127.0.0.1:13429 → 192.168.10.84:3425`.

```
$ curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:13429/v1/models          # no key
401
$ curl ... -H 'Authorization: Bearer <wrong-lab-key>' …                            # wrong key
401
$ curl ... -H 'Authorization: Bearer <valid lab key>' …                               # valid key
200
$ curl ... -H 'x-api-key: <valid lab key>' http://127.0.0.1:13429/v1/magpie/limit
{"key":"lab-…","limited":false}
```

Probe server behind the same path (bound `0.0.0.0:19002`):

```

```

So Magpie sees the provider's own LAN address — non-loopback ⇒ `local()` false ⇒ 401
without a key, 401 with a wrong key, 200 with a valid key, and `keyLimited`/`budget`

### 3.4 Not exposing anything but the gateway port

`--tcp-whitelist` is **not enough** for this design. **VERIFIED**,
`easytier-core/src/config/peers.rs:75–121`: the whitelist is compiled into an *Inbound*
ACL chain (allow the listed TCP ports, drop all other TCP). Inbound means "addressed to
this node's virtual IP", which in no-TUN is the loopback rewrite. Traffic to an exported
**proxied network** goes through the *Forward* chain instead and is unaffected.

**REPRODUCED**, in this order:

| Config on provider | `→ 10.44.0.1:19000` (inbound) | `→ 192.168.10.84:19002` (proxied) | `→ 192.168.10.84:3425` |
| --- | --- | --- | --- |
| `--proxy-networks` only | 200 | **200 (exposed)** | 200 |
| `+ --tcp-whitelist 3425` | refused (timeout) | **200 (still exposed)** | 200 |
| `+ ACL Forward chain, default Drop, allow tcp 3425` | refused | **refused (timeout)** | 200 |

The working provider config is in `docs/validation/lab/provider-acl.toml` (network secret
left as a placeholder). The ACL is the one from `easytier-cli acl set`'s documented shape,
applied at startup through the config file because **`easytier-cli acl set` does not exist
in the released 2.6.4 CLI** (it exists in the repository's newer `easytier-cli.rs:330`;
UNKNOWN whether it ships before the next release — runtime ACL changes were not possible
here).

One more exposure exists regardless of EasyTier: with `lan: true`, Magpie listens on
`*:3425`, so the physical LAN can reach the gateway too (key required, allow list
applies). This machine has no second host, so "reachable from another LAN host" is
**UNKNOWN**; the socket binding is `*:3425` (VERIFIED by `lsof`).

## 4. Priority 2 — Gateway Key quota semantics

All of this section was measured on the **second, portable** Magpie instance
(`127.0.0.1:3426`) using its own key `quota-lab`, calling through its remote-magpie
provider (so every call also traversed the overlay), except where "provider side" is
stated. Nothing here touched the user's keys; both lab keys on the real instance were
removed afterwards.

Costs are Magpie's **estimate at the prices it shows on the Usage page**, not the vendor's
invoice (`internal/access/limit.go:19–20`).

### 4.1 Where the checks are

| Question | Source | Behaviour |
| --- | --- | --- |
| Which requests are limited | `budget.go:28–30`, `gateway/key_limit.go:36–44` | only POSTs whose caller resolved to a key **with** at least one limit; reads, `/mcp/`, `/_magpie/`, `count_tokens` pass |
| Pre-request check | `budget.go:341–372` | refuse when `used + reserved ≥ cap` for **any** limit |
| Reservation | `budget.go:375–414`, `:387` | `body_bytes/4 + mean output of this window's calls`, charged in cost only when a mean cost/token exists, else at the model's input price |
| Settlement | `budget.go:155–176` | the request's own usage record is added to every limit window, from `usage.jsonl` |
| Persistence | `budget.go:132–142` | windows are recomputed from `usage.jsonl`, so a restart cannot lose or double-count |
| Counting rule | `budget.go:98–101` | refused and self-reported records don't count |
| Cost cap granularity | `access/limit.go:147` | `math.Round(cost*1e4)/1e4` — **1/10000 USD**, and `Valid()` returns "no limit" when the rounded value is 0 (`:117–123`) |

### 4.2 Test A — a key with a 1 USD day limit

```
$ magpie gateway-key limit <id> day --cost 1
Cost    $0.00 used of $1.00, $1.00 left (estimate at Usage prices)
$ curl ... -H 'Authorization: Bearer <key>' -d '{"model":"…deepseek-flash","max_tokens":8, …}'
200
$ curl -H 'Authorization: Bearer <key>' http://127.0.0.1:3426/v1/magpie/limit
{"limit":{"period":"day","start":"2026-10-29T00:00:00+08:00","reset":"2026-10-30T00:00:00+08:00",
 "calls":1,"tokens":40,"cost":9.6e-06,"costLimit":1,"costLeft":0.9999904,"spent":false}}
```

**PASS.** One call = 40 tokens = **$0.0000096** for this tiny prompt; `GET /v1/magpie/limit`
is the exact, script-friendly status (the CLI rounds to cents, which is useless at these
sizes).

### 4.3 Test B — raising the cap keeps the usage and resumes at once

```
$ magpie gateway-key limit <id> day --cost 2
Cost    $0.00 used of $2.00, $2.00 left        # used kept: calls 1, cost 9.6e-06
$ ... next call
200   → {"calls":2,"tokens":80,"cost":1.92e-05,"costLimit":2}
```

**PASS.** No reset, no re-creation of the key, effective immediately, no restart. This is
the mechanism the wallet intends to use: *buying credit = raising the same key's cap*.
Measured again end to end over the overlay with a spent provider key and a top-up from
40 to 80 tokens: the consumer went from `429` to `200` on the next request
(`magpie gateway-key limit <id> day --tokens 80`), usage preserved.

### 4.4 Test C — one call that goes over the budget

Token cap 100, current usage 0, sequential calls of 40 tokens each:

| Call | HTTP | used after | state |
| --- | --- | --- | --- |
| 1 | 200 | 40 | open |
| 2 | 200 | 80 | open |
| 3 | **200** | **120** | spent (over cap) |
| 4 | **429** | 120 | spent |
| 5 | 429 | 120 | spent |

```
{"error":{"type":"rate_limit_error","message":"magpie gateway key \"quota-lab\" has used 120
 of its 100 input, output and cache-write tokens for this day; it resets at 2026-10-30 00:00 CST"}}
Retry-After: 14992
X-Magpie-Limit-Reset: 2026-10-30T00:00:00+08:00
X-Should-Retry: false
```

**PASS as documented, FAIL as a billing meter.** The pre-check is done once, before the
call, so a single request can exceed what is left (here +20% of the cap, a full extra
call). The refusal is a clean 429 with reset time and no retry hint. Same with a cost cap
(`--cost 0.0001` after `0.000106` used ⇒ spent).

### 4.5 Test D — concurrency

Token cap 100, usage 0, **five simultaneous** requests (each 40 tokens, body ~106 bytes):

```
parallel 1: 200 1.309538s
parallel 2: 200 1.310314s
parallel 3: 200 1.309164s
parallel 4: 200 1.309510s
parallel 5: 429 0.000691s
{"error":{"message":"… has used 0 of its 100 input, output and cache-write tokens,
 with 4 requests in flight holding the rest …"}}
after: {"calls":4,"tokens":160,"tokenLimit":100,"spent":true}
```

**REPRODUCED.** 4 of 5 admitted, 160 tokens spent against a 100-token cap = **160 % of the
cap**. Reservations are `body/4 + mean output` (`26 + 0` here), far below the real 40, so
the fifth is the only one refused. The absolute overshoot is bounded by *in-flight count ×
real call size*, not by "about one call". Any prepaid design must budget for this (e.g.
reserve the excess, or treat the cap as a soft ceiling with a fixed overdraft).

### 4.6 Test E — boundaries

| Case | Command | Result |
| --- | --- | --- |
| Sub-grid cost cap | `gateway-key limit <id> day --cost 0.000024` | **`quota-lab: no limit` — the key becomes UNLIMITED** (rounded to 0 ⇒ `Valid()` drops the limit) |
| Half-step rounding | `--cost 0.00005` | stored as `0.0001` |
| Smallest usable cap | `--cost 0.0001` | kept (1/100 USD) |
| Zero | `--cost 0` | error `say --tokens, --cost or both, or off for no limit` — a zero cap cannot be set, and `Cost: 0` means "no cap" |
| No cap | `off` | `{"limited":false}` |
| Cycle window | `1h --cost 0.01` | `Window this 1-hour cycle, 19:49 – 20:49`, `start` pinned to when the limit was set (`Limit.Window`, `access/limit.go:187–211`) |
| Reset | `limit <id> reset` | usage 0, same window start; **errors when the key has no limit** (`This key has no limit to reset`) |
| Calls made while unlimited | a key with no limit, then a limit added | the earlier calls **count retroactively** (window read from `usage.jsonl`): 160 tokens appeared as soon as the cap was set |
| Restart | kill and restart the gateway, same data dir | limit, cycle anchor and counts identical (`{"calls":1,"tokens":40,"cost":9.6e-06,"start":"…19:49:45…"}` before and after) |
| Failed upstream | a model the provider key may not use (403) | no tokens/cost charged, reservation released (`inFlight` back to 0), the record is marked rejected |
| Refused request | 429 | not counted in `calls`/`tokens` |
| Price change | — | **UNKNOWN**: historical cost is recomputed at today's prices (`usage.NewCoster` in `budget.read`), but changing the user's provider price was out of scope |
| Window expiry | — | **UNKNOWN** (would need a real day/week or a clock change); the reset path above exercises the same `Window()` anchor |
| Multi-limit key (5h + week) | — | **UNKNOWN** in this lab; both would be enforced (`budget.Reserve` loops all limits), not tested |

### 4.7 What this means for a prepaid wallet

1. The cap is a **soft ceiling**: a purchase of $X buys *at least* $X and *at most*
   X + (one burst of concurrent calls). Prepaid credit must therefore be
   `deposit − overdraft_tolerance`, or the provider accepts the overrun.
2. Cap granularity is **$0.0001**. Never write a smaller cap: it silently disables the
   limit. The plugin must read the value back after writing and treat
   `limited: false` as an error.
3. Raising the cap is atomic, immediate, idempotent and survives restarts — a good
   primitive for "deposit confirmed ⇒ `gateway-key limit <id> … --cost <new cap>`".
4. Usage is shared across limits of a key and across restarts, and includes calls made
   before any cap existed.
5. A cap of 0 (or a rounded-to-0 cap) is *unlimited*, not *blocked*. Reconcilers must
   never compute "cap 0" to mean "stop this consumer".

## 8. Answers to the three questions

**Q1 — Can the separate HTTP billing entry point be dropped and Magpie's Gateway Key
carry both admission and charging?**
**Yes, with two conditions.**
Admission, model scoping, per-request enforcement, usage accounting, stream settlement,
restart-safe state and immediate top-ups are all native and were measured (§4). Conditions:
(a) the consumer must send its key on **every** request and the ingress must make the
request non-local (§3.3); (b) the key's cap is a soft ceiling with $0.0001 granularity and
a concurrency overshoot (§4.4–4.6), so prepaid credit must be issued as
`cap += deposit − tolerance`, capped values must be read back, and 0 must never mean
"blocked". No second gateway is needed.

**Q2 — Can EasyTier no-TUN carry a remote Magpie safely under Gateway Key auth without
exposing unnecessary ports?**
**Yes, but not with the plain no-TUN virtual-IP port forward.** That path is rewritten to
`127.0.0.1` (source and measurement, §3.1) and Magpie trusts loopback, so a peer can call
without any key (§3.2, FAIL). The native combination that works is: provider
`--no-tun` + `proxy_network = [<own LAN IP>/32]` + inbound `tcp_whitelist` + a
**Forward-chain ACL** that allows only TCP 3425, consumer `port-forward` to
`<provider LAN IP>:3425`. Measured: 401/401/200 for none/wrong/valid keys, every other
local port unreachable (§3.3–3.4), and the quota enforcement follows the key (§4). Open
items: the physical LAN still reaches `*:3425` (needs a pf/allow-list decision, untested
from a second host), and `easytier-cli acl set` is missing in 2.6.4, so ACL changes mean a
config rewrite + restart.

**Q3 — What is the minimum set of plugin modules for the next phase?**
1. **EasyTier supervisor** — generate the provider/consumer TOML (with the ACL and
   whitelist), start/stop `easytier-core`, own the `--rpc-portal`, and add/remove port
   forwards through `easytier-cli`.
2. **Key provisioner** — create one held key per consumer (`gateway-key add`,
   `models <id> …`, `limit <id> day|Nd --cost|--tokens …`), never unrestricted (§3.5),
   never a sub-$0.0001 cap (§4.6), and read back `/v1/magpie/limit` to confirm.
3. **Top-up / reconcile worker** — idempotent `cap = f(verified deposits, consumed)` with
   the overdraft and granularity rules above, plus a periodic comparison against
   `/v1/magpie/limit` (the consumer key can read its own numbers only).
4. **Deposit watcher (testnet)** — Base Sepolia USDC `Transfer` logs, dedupe key
   `(chain, token, tx, logIndex)`, durable intent state before broadcasting anything.
5. **Page** — read-only balance/history (the page cannot write, by design) plus a host
   service for actions.
No Magpie or EasyTier patch is required for 1–5.

## 9. Confirmed limitations and open questions

Confirmed (this machine, these versions):

- Loopback is trusted; any ingress that lands on `127.0.0.1` bypasses keys **and**
  budgets. EasyTier no-TUN's virtual-IP forward does exactly that.
- `--tcp-whitelist` does not restrict exported proxied networks; a Forward ACL does.
- `--proxy-networks <own address>/32` is a working, keyed ingress.
- An unrestricted consumer key can read the provider's quota/usage/concurrency endpoints;
  a held key cannot.
- Caps: soft ceiling, one-call (or one-burst) overshoot, $0.0001 grid, sub-grid values
  silently disable the cap, `0` = uncapped, top-ups immediate and non-destructive,
  restart-safe, calls before the cap count.
- Remote Magpie works over the overlay for Chat, Responses, Messages, streaming and native
  groups, and reports the remote's key refusals.

Open (UNKNOWN until measured elsewhere):

- Two real computers on different networks, NAT traversal through a HK relay, and real
  latency/timeouts.
- Windows and Linux behaviour (paths, firewall, service supervision, ACL file).
- Whether `*:3425` on the physical LAN is reachable from another LAN host, and whether
  `MAGPIE_ALLOW_IPS` alone is an adequate guard there (`ownAddr` is always allowed, so it
  cannot separate the overlay path from a local proxy path on the same address).
- Price-change recomputation of historical usage; multi-limit keys; window expiry on a
  real clock; Magpie restart **while requests are in flight** (reservations are memory
  only).
- EasyTier `acl set` at runtime (absent in 2.6.4) and credential-mode/secure-mode pinning
  as a replacement for the shared `network_secret`.
- End-to-end installation of a community plugin (npm/local folder) and its Bun host
  actually invoking the Magpie CLI; only the source-level capability was verified.
- Whether Magpie's plugin host could be considered part of the trust boundary for wallet
  secrets (it runs third-party code with full user privileges).
